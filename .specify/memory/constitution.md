# Tomato Todo 项目章程

## 核心原则

### I. 用户体验优先

所有设计决策必须以用户体验为中心。界面必须简洁、直观、响应迅速。避免不必要的复杂性,确保功能易于发现和使用。

**理由**: 桌面小组件的核心价值在于快速、无干扰地提供功能,良好的用户体验是产品成功的基础。

### II. 简单性

遵循 YAGNI(You Aren't Gonna Need It)原则。只实现当前需要的功能,避免过度设计。代码应该简单、直接,避免不必要的抽象层。

**理由**: 简单的代码更容易理解、维护和扩展。过度设计会增加复杂度和维护成本。

### III. 模块化架构

应用必须采用模块化设计,将番茄时钟、TodoList、UI 组件等功能分离。模块之间通过明确定义的接口通信,最小化耦合。

**理由**: 模块化架构使代码更易于测试、维护和扩展。每个模块可以独立开发和演进。

### IV. 代码质量

代码必须遵循统一的编码规范和最佳实践。包括但不限于:
- 清晰的命名(中文注释)
- 适当的错误处理
- 合理的性能优化
- 必要的日志记录

**理由**: 高质量的代码减少 bug,提高可维护性,确保长期稳定性。

### V. 可维护性

代码必须易于理解和修改。优先考虑代码的可读性而非巧妙性。复杂的逻辑必须添加注释说明设计意图和实现细节。

**理由**: 可维护的代码降低了修改成本,使团队能够快速响应需求变化。

## 技术约束

### 平台要求

- **目标平台**: Windows 10 及以上版本
- **应用类型**: 桌面小组件(Desktop Widget)
- **窗口特性**: 支持悬浮置顶、大小可调整

### UI 设计标准

- **设计风格**: 扁平化设计,去锐利化(圆角、柔和阴影)
- **视觉语言**: 简洁、现代、专业
- **交互原则**: 直观、流畅、响应迅速
- **参考标准**: 业界通用 UI/UX 最佳实践(如 Fluent Design、Material Design 等)

### 技术栈要求

- 选择成熟、稳定的桌面应用开发框架
- 优先考虑跨平台能力(为未来扩展预留空间)
- 确保 UI 框架支持自定义窗口样式和动画效果

## 开发工作流程

### 测试要求

- 核心业务逻辑必须有单元测试覆盖
- 关键用户交互必须有集成测试
- UI 组件必须有自动化测试或详细的手动测试指南
- 测试必须在代码合并前通过

### 代码审查

- 所有代码必须经过审查才能合并
- 审查重点关注:代码质量、设计一致性、潜在 bug
- 审查者必须理解代码的上下文和意图

### 文档要求

- 核心 API 和公共接口必须有文档说明
- 复杂的业务逻辑必须有注释和设计文档
- 用户可见的功能必须有使用说明
- 关键的设计决策必须记录在案

### 版本管理

- 遵循语义化版本规范(SEMVER)
- 主版本号:不兼容的 API 变更
- 次版本号:向下兼容的功能性新增
- 修订号:向下兼容的问题修正

## 治理

### 章程地位

本章程是项目开发的最高指导原则,优先于所有其他实践和习惯。所有开发决策必须符合章程规定。

### 修正流程

- 章程修正需要明确的理由和 documented 的讨论
- 修正必须更新版本号并记录变更原因
- 重大修正需要提供迁移计划,确保现有代码符合新要求

### 合规审查

- 每个 Pull Request 必须验证是否符合章程原则
- 定期审查代码库,识别违反章程的模式并制定改进计划
- 复杂性增加必须得到充分证明,避免不必要的复杂设计

### 运行时指导

开发过程中参考 `.specify/templates/agent-file-template.md` 获取项目特定的技术指导、命令和代码风格要求。
